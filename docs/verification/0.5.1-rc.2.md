# 0.5.1-rc.2 verification record

These are maintainer tests, including real installed collections and controlled
native agent trials. They are not external participants or a reliability
benchmark. Final source commit, package checksums and CI results accompany the
[prerelease](https://github.com/tangericm/skillcrit/releases/tag/v0.5.1-rc.2).
The [RC1 record](0.5.1-rc.1.md) remains historical evidence for the earlier build.

## Large reports exposed an RC1 bug

On September 5, 2026, `doctor --user --json` on a real installed collection
produced only 65,536 bytes through a pipe, ending inside a JSON string. The
same failure reproduced on Node 24.20.0 and 26.7.0. The CLI called
`process.exit()` immediately after queuing output, discarding pending writes.

The fix sets `process.exitCode` and lets output drain. Three regression tests
first failed with truncated JSON, then passed after the fix. They exercise 256
skills through real processes: complete scan (exit 0), lint findings (exit 1),
and incomplete doctor coverage (exit 3). All three are also shipped in the
simulation script, bringing it to 16 scenarios. This follows Node's documented
[process output behavior](https://nodejs.org/api/process.html#processexitcode).

The corrected audit returned valid JSON of approximately 4.4 MB containing 545
skill files. It retained exit 3 and six coverage warnings for deep plugin trees
and script limits. This is a usable partial report, not a complete machine
inventory. Raw reports remain local because they contain paths and skill text.
CLI help now states that doctor exit 0 means completed coverage, not no findings.

Ten findings from the Superpowers collection were reviewed: token/line budgets

remain hypotheses about related descriptions, not observed runtime contention.

corrected: `pip install -r requirements.txt` does not establish unpinned
resolution. The rule now asks the reader to inspect requirements and lockfiles
before changing commands. No vulnerability or beneficial deletion was inferred
from these results. Informational wording and overlap heuristics still need
feedback from real users.

## Native activation

Trials used Claude Code 2.1.260, Codex CLI 0.147.0, and Cursor desktop 3.19.7 on
macOS. Each trial started a fresh agent conversation. The positive prompts
asked about overlapping skills or context cost without naming Skillcrit or
supplying its executable path. A built CLI was available on PATH. Fixtures
contained controlled Read/Bash permission variants; no private collection was
submitted to another client for these trials.

| Client / route | Observed result |
| --- | --- |
| Codex, `.agents/skills` | Selected the local Skillcrit instructions and ran the CLI in both duplicate and cost trials; did not run it for an unrelated note-summary task |
| Claude, local plugin via `--plugin-dir` | Called `skillcrit:skillcrit` and ran the CLI in both duplicate and cost trials; did not call it for the unrelated note-summary task |
| Cursor, `.cursor/skills` | Native slash-command selector discovered Skillcrit; explicit trial ran the supplied CLI on the correct project; a fresh ordinary duplicate-audit prompt selected Skillcrit and ran it from PATH |
| Cursor, incomplete project | A fresh ordinary audit prompt ran the CLI, reported exit 3 and incomplete coverage, and rejected cleanup on partial evidence |

Fixture file hashes remained unchanged. Agents preserved runtime uncertainty
and treated risk findings as review signals. The initial Claude plain-folder
probe used disabled setting sources and discovered instructions by reading
files; it is not counted as native automatic activation. The plugin trials
above exercised the native Skill tool directly.

These are a few observed successes, not an activation-rate measurement. The
CLI prerequisite was prepared by the maintainer; this does not establish that
an unaided new user can install everything successfully. Trials used local
candidate builds; the final release package receives separate install and
simulation checks. Client defaults selected their models.

## Cursor plugin installation

Cursor 3.19.7 rejected a local plugin symlink whose target was outside
`~/.cursor/plugins/local`; its native plugin log identified the containment
check. Copying the manifests, bundled skill and referenced icon into an actual
directory under that root succeeded. Customize displayed **Skillcrit**,
**Local**, **0.5.1-rc.2**, and **Skills 1**. No security setting was changed.
For this client version, use a real directory for local testing even though
current vendor documentation also describes symlinking. This verifies local
installation/discovery; the live audits above used the plain-skill route.

## Same-name skills and namespaces

Codex's native `skills/list` returned both enabled `precedence-probe` entries
from a repository root and a nested project's `.agents/skills`. This proves
both were discovered; it does not select a runtime winner.

Claude loaded two disposable plugins, each providing `precedence-probe`.
Explicit calls to `probe-a:precedence-probe` and `probe-b:precedence-probe`
returned their distinct expected markers. Thus neither namespaced copy was
redundant merely because the unqualified skill names matched. Fixture hashes
were unchanged.

Cursor displayed one `precedence-probe` command for `.cursor/skills` and
`.claude/skills` copies in the same project. Explicit invocation returned the
marker from the `.cursor` copy. This is one observed selection in that layout,
not evidence about user, admin, plugin or marketplace precedence.

These observations reinforce the product's `runtimeResolution: "unknown"`
contract. They are not a universal client precedence algorithm.

## Remaining release and adoption gates

Require a reviewed commit, the six OS/Node CI combinations, successful SARIF
ingestion, a clean-source package build, an isolated package installation,
all 16 installed simulations, and download checksum agreement. The release
attachments record the final results. npm publication additionally requires
maintainer authentication and a verified registry installation.

Cursor CLI was installed from its official vendor source but requires its own
sign-in; desktop evidence above comes from the already authenticated application.
Public marketplace approval, external pilot participation, voluntary repeat
use, and stable promotion are still open. Simulated users cannot satisfy those
criteria. See the [pilot guide](../pilot-guide.md).
